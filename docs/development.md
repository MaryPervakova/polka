### Режим первого запуска

Рекомендация: `manual strict`. В `manual` пользователь согласует спецификацию и план перед разработкой; `strict` ограничивает проработку границами исходного задания. Режим не выбран за пользователя и сам по себе не закрывает открытые вопросы. Точные правила режима навык читает при запуске, по своей последовательности фаз.

Будущий запуск должен явно задавать объём: весь MVP с командным запуском либо конкретный этап/функцию. Для полного MVP условия SSO остаются частью требований; для отдельного этапа они сохраняются в дорожной карте. Ограничение текущего запуска не удаляет требование из продукта. Пока действует поручение только на документы, работа заканчивается подготовкой документации и рекомендаций: реализация и установка зависимостей требуют нового поручения.

### Этапы и проверки

Навык ведёт этапы «Подготовка», «Требования», «Брифинг», «Спецификация», «План», «Разработка», «Код-ревью», «Приёмка». Детальные файлы фаз читаются тогда, когда начинается соответствующая фаза; этот документ не заменяет их.

- После брифинга у каждого требования есть статус и основание. Вопросы из Q не считаются закрытыми по умолчанию.
- Спецификация должна покрыть требования объёма запуска и пройти независимую проверку полноты. Неразрешённый вопрос, влияющий на этот объём, блокирует соответствующую проверку; его нельзя скрыть, назвать готовым или исключить без решения пользователя.
- В `manual` спецификация и затем план предъявляются пользователю для согласования. Текущая архитектура со статусом «предложение» не заменяет это согласование.
- План связывает каждый таск с требованиями; расширения продукта требуют решения пользователя.
- При разрешённой реализации навык поручает код субагентам и организует код-ревью. Вне запуска autopilot этот раздел сам по себе не поручает создавать субагентов.
- Приёмка проверяет исходное задание независимо от спецификации. Способы проверки и условия чистого клона задаёт навык; пока Git-репозитория и приложения нет, такая приёмка не выполнена.

Развёртывание, публикация, платные и необратимые операции выполняются по действующему разрешению пользователя и правилам подтверждения применимых инструментов. Запуск навыка не превращает их автоматически в разрешённые действия. Секреты в документы и задания субагентам не записываются.

## Подготовка технической работы

1. Подготовить предложение стека для согласованного локального этапа (Q-11), опираясь на прочитанную документацию IC Kit. Корпоративные параметры и готовый SSO получить до серверного/командного запуска. Фактическую совместимость проверить при разрешённой реализации; пакеты в рамках текущего поручения не устанавливать.
2. Использовать утверждённые React/TypeScript/Vite/CSS/sx/tsx и Excel. Согласовать оставшиеся серверные детали, способ чтения/записи книги и поддержку sx; PostgreSQL повторно не предлагать вместо решения пользователя.
3. Определить листы/колонки книги, преобразования версий структуры, контракты, очередь сохранения, блокировки и резервирование. Валидация заполненных значений сохраняется, полнота карточки не требуется.
4. После отдельного поручения на реализацию создать конфигурацию проекта и документировать фактические команды.

До записи нужны копия данных и проверяемый способ отката импортированной партии; это рекомендация процесса переноса, не реализованный механизм. После импорта инициатор сверяет результат и исключения.
