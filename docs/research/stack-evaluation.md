## PostgreSQL с начала или SQLite

SQLite пригодна для локального приложения и многих сайтов с небольшой/средней нагрузкой. У неё один одновременно выполняющийся писатель; короткие записи могут успешно ожидать очереди. Доступ пользователей к приложению по сети сам по себе не исключает SQLite, если SQL выполняется сервером рядом с файлом базы. Следовательно, утверждение «SQLite не подходит небольшой команде» было бы неверным. [Рекомендации самих авторов SQLite](https://www.sqlite.org/whentouse.html).

**Рекомендация для «Полки»: PostgreSQL уже локально и затем на сервере.** Основание — ожидаемый переход к корпоративному размещению и возможность сохранить один SQL-диалект, ограничения целостности и процедуру миграций. Это проектный выбор, а не техническая невозможность SQLite. Цена — локальная служба базы, настройка доступа, обновления и резервирование. SQLite проще на первом компьютере, но переход на PostgreSQL потребует отдельной проверки типов, запросов, поиска, ограничений и переноса данных; без фактической модели стоимость не измерена.

Для начала предлагаются нумерованные SQL-миграции и `pg`, без предварительного выбора ORM. Нужны учёт применённых миграций, защита от параллельного запуска и проверка развёртывания на пустой базе и обновления существующей. Это рекомендация устройства, готового инструмента миграций пока нет.

## Превью и перенос

Предлагается хранить файлы превью вне публичного каталога сборки, в базе — метаданные и связи. Выдавать их через сервер после проверки прав. Это рекомендация по границам доступа из архитектуры, не подтверждённая реализация. Для одиночного серверного размещения файловое хранилище может сохраниться; объектное хранилище выбирается при появлении соответствующих требований среды.

Перенос означает перенос **базы и файлов**, а также настроек и прав. PostgreSQL предоставляет `pg_dump` для логической копии и последующего восстановления базы; это не копия внешних файлов превью. [SQL dump PostgreSQL 18](https://www.postgresql.org/docs/18/backup-dump.html). До накопления рабочих данных требуется определить согласованное резервирование базы/файлов, место копий и проверить восстановление. Простое копирование каталога работающей базы не предлагается.

## Что остаётся проверить

- По read-only проверке окружения основным агентом доступны macOS 15.7.4 arm64, Node v26.13.0 и npm 12.2.2; `psql` и `docker` в PATH не найдены. Это не доказывает отсутствие PostgreSQL или Docker вне PATH. Способ локальной установки базы пока не выбран и не выполнен.
- После разрешения реализации: установка фиксированных зависимостей, smoke test IC Kit с React/Vite/Node, сборка клиента, запуск Fastify и проверка `pg` с выбранной PostgreSQL. Только затем закрепить окончательные версии.
- До постоянной серверной эксплуатации: поддерживаемое применение IC Kit, ОС/ресурсы и доступные версии компании, диски/резервные копии, домен/TLS и порядок обновлений.
- Корпоративный SSO ещё разрабатывается; протокол и контракт ролей неизвестны (Q-10). Не выбирать OAuth/OIDC/SAML по предположению и не открывать командный доступ вместо интеграции. Локальный режим инициатора проектируется отдельно.
- Технические пределы загрузок, полей и запросов остаются Q-11. Числа не выводятся из значений по умолчанию библиотек. Импорт по-прежнему требует восстановленных исходного снимка и отчёта исключений.

Проверка охватывает документацию и аргументацию выбора; тесты приложения, нагрузка, восстановление резервной копии и совместимость в «Полке» не проверены.
